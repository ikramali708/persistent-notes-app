## 1. How to Run

**Backend (ASP.NET Core):**
```bash
cd backend
# Update connection string in appsettings.json with your SQL Server name
dotnet ef database update
dotnet run
```
Backend runs at `https://localhost:7278`  
Swagger: `https://localhost:7278/swagger/index.html`

**Frontend (React + Vite):**
```bash
cd frontend
npm install
npm run dev
```

## 2. Stack Choice

**What I chose:** React + Vite (frontend) · ASP.NET Core Web API + EF Core (backend) · SQL Server (database)

**Why this stack:**
- **ASP.NET Core** gives a strongly-typed, production-grade REST API with minimal boilerplate. EF Core handles migrations cleanly — one command (`dotnet ef database update`) sets up the database on any machine.
- **SQL Server** is a fully relational database — notes with relationships (future: tags, users) stay consistent and queryable without extra setup.
- **React + Vite** gives instant HMR for fast frontend iteration. Component-based structure kept the UI logic clean and separated.

**What would have been a worse choice and why:**
Using a JSON file on disk as storage would have been simpler to start but would break immediately with concurrent writes, have no query support, and produce data corruption with abrupt shutdowns — exactly the kind of persistence failure the assessment is testing against. localStorage would fail the "restart the app" requirement entirely since it lives only in the browser.

## 3. One Real Edge Case

**Edge case: Pinning a note that was just deleted by another tab**

**File:** `frontend/src/services/noteService.js` — `togglePin` function  
**File:** `backend/Controllers/NotesController.cs` — `PATCH /api/notes/{id}/togglepin`

**What happens:**  
If a user opens the app in two browser tabs, deletes a note in Tab A, then clicks the Pin button for that same note in Tab B (before Tab B refreshes), the frontend sends a `PATCH` request for an ID that no longer exists in the database.

**Without handling:** The backend throws a `500` or `404`, EF Core tries to update a non-existent record, and the frontend shows a generic error toast — but the note list in Tab B still shows the deleted note as if it exists, causing a ghost card stuck in UI.

**How it is handled:**  
The backend returns `404 Not Found` when the note ID does not exist. The frontend `.catch()` block in `togglePin` catches the error and calls `toast.error("Update failed")`. After any pin/delete/edit action, `loadNotes()` is called — this re-fetches the current server state and clears any ghost cards from the UI.

## 5. Honest Gap

**What is not good enough:**

There is no optimistic UI update — every action (add, edit, delete, pin) waits for the backend to respond and then calls `loadNotes()` to re-fetch the entire list. On a slow connection this feels sluggish: you click "Add Note" and nothing happens visually for a moment until the server responds and the list reloads.

**What I would do with another day:**

Implement optimistic updates — immediately update the local `notes` state on the frontend when the user takes an action, and only roll back if the server returns an error. For example, on delete: remove the card from state instantly, show the toast, and if the API call fails, add the note back and show an error. This would make the app feel instant and responsive regardless of network speed.

I would also add **debounced search** on the backend instead of filtering on the frontend — right now if there are thousands of notes, all of them are fetched and filtered in the browser, which would not scale.
