## 1. How to Run

**Backend:**
```bash
cd backend
# Set your SQL Server name in appsettings.json under ConnectionStrings
dotnet ef database update
dotnet run
```
Runs at `https://localhost:7278` — Swagger at `/swagger/index.html`

**Frontend:**
```bash
cd frontend
npm install
npm run dev
```
Runs at `http://localhost:5173`

## 2. Stack Choice

**Chose:** React + Vite · ASP.NET Core Web API · Entity Framework Core · SQL Server

**Why:**
- I already had experience with ASP.NET Core and EF Core, so I could set up a clean REST API quickly without fighting unfamiliar tooling.
- EF Core migrations make database setup on a fresh machine very simple — one command (`dotnet ef database update`) creates all tables automatically.
- SQL Server is reliable for relational data. Notes can later have tags, categories, or user ownership without restructuring anything.
- React with Vite gave fast hot reload during development, which helped when iterating on UI quickly.

**What would have been worse:**
Using a plain JSON file for storage would have been the worst choice. It has no support for concurrent access, no querying, and corrupts easily if the app crashes mid-write. It also would not scale beyond a few hundred records. localStorage would fail the persistence requirement entirely since it only lives in the browser and disappears on clear.

## 3. One Real Edge Case

**Edge case: Deleting a note that is being edited at the same time**

**File:** `frontend/src/App.jsx` — `handleDelete` function  
**File:** `backend/Controllers/NotesController.cs` — `DELETE /api/notes/{id}`

**What happens:**
If the edit modal is open for a note and the user somehow triggers delete for that same note (e.g. through another tab or a fast double action), the frontend sends a `DELETE` request. The modal is still open with the old note data. When the user clicks "Save Changes", the frontend sends a `PUT` request for an ID that no longer exists in the database.

**Without handling:**
The backend returns `404`, but the modal stays open and the user sees a generic "Failed to update" toast with no explanation. The note list also does not refresh automatically, so a ghost card may remain visible.

**How it is handled:**
After every action (delete, pin, edit), `loadNotes()` is called immediately — this re-fetches the latest state from the server and removes any ghost cards. The `.catch()` on `updateNote` shows an error toast. The edit modal closes on save attempt regardless of success or failure so the user is not stuck.

## 5. Honest Gap

The app re-fetches the entire notes list from the server after every single action — add, edit, delete, pin. This works fine for small data but is inefficient. If a user has hundreds of notes, every button click causes a full reload of all data from the database.

With another day I would implement optimistic UI updates: update the local state immediately when the user takes an action, and only roll back if the server returns an error. This would make the app feel instant even on slow connections, and reduce unnecessary database reads.

I would also move search to the backend with a proper SQL `LIKE` query and pagination, instead of filtering all notes in the browser.
